# Контракт поставки модели сторонним исполнителем

Версия: 1.6 (baseline v7.6 r2 / Lab v0.9.2, 2026-09-25) — §9: исполнитель-агент с доступом к репозиторию; §9.4: агент без локального git

## 1. Распределение ролей

```text
Владельцы проекта (мы)                    Исполнитель
─────────────────────────────             ─────────────────────────────
держат accepted baseline                  получает baseline целиком
пишут спецификацию / test plan            строит candidate ModelJSON
выпускают change-policy ДО реализации     может предлагать свои идеи
прогоняют стенд, ведут документацию       отдаёт: модель + критерии проверки
принимают / отклоняют candidate           НЕ трогает accepted baseline
```

Принцип не меняется с v6.x: **принятые результаты не теряем**. Регрессия относительно accepted baseline недопустима; расширение и намеренное изменение допустимы только явно, через контракт.

## 2. Что исполнитель получает

Директорию baseline целиком:

```text
model/       — accepted ModelJSON (замороженный, SHA в BASELINE_MANIFEST.json)
validation/  — исполняемый validation-контракт принятой версии
policy/      — strict default-deny policy, привязанная к SHA модели и validation
lab/         — Orbital Economy Lab (стенд), готов к INSTALL.cmd
docs/        — спецификации, kernel-контракт, отчёты, этот документ
```

Плюс для конкретной задачи:

- `V<ver>_ARCHITECTURE_SPEC.md` — что должно измениться и почему;
- `V<ver>_TEST_PLAN.md` — какие новые Modes и какие ожидания;
- `change-policy-v<ver>-<name>.json` — заранее выписанный контракт разрешённых изменений (может быть в статусе draft: тогда исполнитель обязан предложить дополнения с обоснованием, а не молча расширить).

## 3. Что исполнитель обязан вернуть

### 3.1 Обязательные артефакты

| # | Артефакт | Требование |
|---|---|---|
| 1 | `candidate ModelJSON` | один файл; `simulation@9.0.0` загружает, `model.check()` = 0 ошибок; `name` содержит версию и ревизию (`… candidate rN`) |
| 2 | `validation-v<ver>.json` | validation-контракт для стенда: все прежние проверки сохранены, новые Modes описаны сценарными проверками (`scenarios`), новые сектора добавлены в `capital_lifecycle_kernel`; новые граничные потоки классифицированы в `open_boundaries` с честным `closed_world`; новые A/B-асимметрии либо отсутствуют, либо задокументированы в `colony_symmetry.exceptions` с причиной |
| 3 | `change-policy-v<ver>-<name>.json` | если выданная policy была draft — финальная редакция с обоснованием **каждого** allow-rule; `accepted_model_sha256` = SHA нашего baseline, `validation_sha256` = SHA артефакта 2 |
| 4 | `CANDIDATE_REPORT.md` | что сделано, что отклонено от спецификации и почему, известные ограничения (в стиле `V7_3_R2_VALIDATION_REPORT.md`) |
| 5 | папка `output\policy-…\` из `CHECK_CANDIDATE.cmd` | доказательство, что исполнитель прогнал полный gate у себя |

### 3.2 Обязательные результаты стенда на поставке

Прогоняются нами на чистой копии baseline с артефактами исполнителя, все Modes:

```text
LIFECYCLE_CONFORMANCE.cmd   → CONFORMANCE RESULT: PASS (0 NON_CONFORMING)
STRUCTURE_AUDIT.cmd         → STRUCTURE AUDIT RESULT: PASS (unclassified=0, symmetry mismatches=0)
                              closed-world violations: не больше, чем в baseline (сейчас 0), если задача не обещала иного
                              unpaired transformation flows = 0; новые пары объявлены и численно проверяются
RUN_LAB.cmd                 → OVERALL: PASS
CHECK_CANDIDATE.cmd         → POLICY RESULT: PASS
                              Unexpected: 0
                              Forbidden: 0
                              Threshold exceed: 0
                              Required missing: 0
                              Hard blockers: 0
```

Для функциональной версии нормальный результат — третий случай из `lab\README_RU.md` §19: `COMPARISON RESULT: DIFFERENT_OUTPUTS` + `POLICY RESULT: PASS`. `DIFFERENT_OUTPUTS` сам по себе — не проблема; проблема — любое отличие, не покрытое policy.

### 3.3 Что НЕ принимается

- изменение файлов в `model\` или `lab\reference\accepted\` — accepted baseline обновляем только мы, отдельным решением;
- policy, расширенная постфактум «чтобы стало зелёным», без объяснения каждого правила;
- `allow` с `name: "*"` без `modes` и без обоснования;
- отключение или ослабление HARD-проверок в validation (tolerance, удаление плагинов, удаление старых сценарных проверок);
- добавление `[Capital Lifecycle Enabled]` к секторам, у которых его не было (Refinery, Transport) — см. `CAPITAL_LIFECYCLE_KERNEL_SPEC.md` §5;
- новый сектор с капиталом, не описанный в `capital_lifecycle_kernel` или `NON_CONFORMING`;
- неклассифицированные граничные потоки; категория с `closed_world: true`, поставленная только чтобы счётчик не рос;
- A/B-асимметрия без причины в `exceptions`, а также «исключение» для экономической (не тестовой) асимметрии — такое описывается в спецификации версии;
- обновление `simulation` или `npm audit fix --force`;
- «унификация» формул / переименование существующих примитивов без отдельной задачи: каждое переименование — это `element_removed` + `element_added` + изменения всех outputs, и policy это увидит.

## 4. Как исполнитель работает со стендом

```text
1. INSTALL.cmd; SELF_TEST, QA_SELF_TEST, COMPARE_SELF_TEST, POLICY_SELF_TEST, CONFORMANCE_SELF_TEST, STRUCTURE_SELF_TEST — всё PASS
2. Прочитать spec / test plan / policy.
3. Положить candidate в lab\input\model\ (ровно один JSON).
4. Итерации:
     LIFECYCLE_CONFORMANCE.cmd   — секунды; структура kernel
     STRUCTURE_AUDIT.cmd         — секунды; открытые границы + A/B-симметрия
     RUN_LAB.cmd --modes=…       — минуты; HARD + сценарии (частичный список Modes допустим для диагностики)
     CHECK_CANDIDATE.cmd         — финальный gate, только Modes=all
5. Разобрать каждый UNEXPECTED / FORBIDDEN / THRESHOLD / NON_CONFORMING / unclassified boundary / symmetry mismatch.
6. Если нужное изменение не покрыто policy — предложить правило с обоснованием в CANDIDATE_REPORT.md, не расширять молча.
```

## 5. Критерии проверки, которые исполнитель поставляет вместе с моделью

Критерии — это не текст, а исполняемый `validation-v<ver>.json`. Минимум для новой версии:

1. **HARD** (всегда FAIL при нарушении): `finite_all`, `non_negative_regex`, плагины `energy_balance`, `capital_lifecycle_kernel` (все сектора с капиталом), `transport_allocator`; новые физические тождества новой механики — как новый плагин или `global_checks`.
2. **REGRESSION**: Modes, которые обязаны воспроизводить accepted поведение, остаются в `regression_modes`; policy для них не содержит `series_changed` allow-rules.
3. **EXPECTATION**: для каждого нового Mode — сценарные `metric` / `event_exists` / `event_order` / `event_absent` проверки, отражающие причинно-следственные ожидания из test plan (например: activation раньше construction; temporary shock не вызывает строительство; recovery через reactivation быстрее, чем через новое строительство).

Проверка должна быть такой, чтобы **её провал был бы содержательной находкой**, а не тавтологией текущего вывода модели. Пороговые значения берутся из test plan, не подгоняются под полученный результат.

## 6. Что мы делаем после приёмки

1. Копируем принятый candidate в `model\`, `lab\input\model\` и `lab\reference\accepted\model\`, обновляем `lab\reference\accepted\manifest.json` и `BASELINE_MANIFEST.json`.
2. Принятый validation становится `validation\` и `lab\input\validation\`; выпускается новая strict policy (`default_action: deny`, `rules: []`) с новыми SHA модели и validation.
3. Перегенерируются `docs\PARAMETER_REGISTRY.md`, `docs\STRUCTURE_AUDIT_REPORT.md`, `docs\CAPITAL_LIFECYCLE_CONFORMANCE_REPORT.md`, обе `SHA256SUMS.txt`; отчёт приёмки и артефакты предыдущей ревизии — в `docs\`.
4. Обновляются `CURRENT_STATE.md`, `HISTORY_RU.md`, `ROADMAP.md`, `lab\docs\TEST_STATUS_RU.md`.
5. С переходом проекта в git «архив предыдущего baseline» — это коммит и тег (`vX.Y-rN`), а не новая директория: в дереве живёт одна принятая версия.

## 7. Вариант: исполнитель не может запускать стенд

Если исполнитель — чат-модель или человек без Node-окружения, схема §3–§4 меняется в трёх местах, остальное действует без изменений:

1. **Поставка модели — патчем**, а не ModelJSON: `model-patch.json` формата `orbital-economy-model-patch-v1` (`lab\docs\MODEL_PATCH_RU.md`). Стенд применяет его к замороженной accepted-модели (`APPLY_PATCH.cmd`) и получает candidate детерминированно. Полная модель от исполнителя не принимается.
2. **Артефакт №5 (собственные прогоны) не требуется.** Вместо него — чек-лист самопроверки в задании (ссылки ↔ LINK, форма IfThenElse, симметрия A/B, пространства имён).
3. **Итерации через нас.** На каждую поставку мы прогоняем `APPLY_PATCH → LIFECYCLE_CONFORMANCE → STRUCTURE_AUDIT → RUN_LAB → CHECK_CANDIDATE` и возвращаем Markdown-отчёты стенда; исполнитель правит патч. `validation_sha256` для policy сообщаем мы. Пороги `[calib]` исполнитель заполняет после того, как увидит числа в наших отчётах.

Приёмка по-прежнему выполняется на нашей чистой копии baseline; критерии §3.2 не меняются.

## 8. Уроки прошлых задач — обязательны для следующих заданий

### Задача 001 (v7.4)

1. **Спецификация проверяется на реализуемость до выдачи**: минимальный skeleton-patch, применённый стендом, должен хотя бы запуститься в новых Modes. r1 задачи 001 упал на алгебраической петле через общий энергетический аллокатор — дефект спецификации стоил исполнителю итерации.
2. **Пороги EXPECTATION задаются после первого прогона**, а не до: r0-пороги «going concern per colony», «expansion > 1e-6 = старт строительства», «восстановление ≥ 0.05» оказались либо бессмысленными в новом мире, либо ложно срабатывающими. В первой итерации validation содержит HARD + REGRESSION + качественные ожидания; числа — со второй.
3. **Реестр внешних параметров** (`docs/PARAMETER_ANNOTATIONS.json`): новые константы кандидата аннотируются исполнителем в отчёте (роль / что меняет / доказательство); мы переносим в реестр при приёмке. Неаннотированная несимметричная пара A/B — замечание к поставке.
4. Исполнитель-LLM работает хорошо, когда получает дословный working context; его собственные наблюдения (watch items) надо читать внимательно — в 001 он предсказал вторую проблему до прогона.

### Задачи 002 (v7.4.1) и 003 (v7.5)

5. **Skeleton-патч до выдачи окупается**: 002 и 003 получили проверенный skeleton и дословный working context; 002 принята с первой итерации, у 003 все замечания были содержательные, а не «не запускается».
6. **Skeleton должен покрывать обе колонии.** В 003 проверка «B производит оборудование» была написана нами и заведомо ложна: B в принятом baseline не расширяется ни в одном секторе, спрос на оборудование = 0. Skeleton прогонялся только для A и этого не показал.
7. **Мягкое нормирование должно быть безмасштабным.** `Inv / (Inv + const)` неявно фиксирует масштаб колонии: при целевом запасе «N дней спроса» буфер тоже задаётся в днях спроса, иначе колония с малым спросом «недообслужена» в равновесии.
8. **Парное тождество — только в тех Modes, где поток включён.** Гейтированный поток при выключенном переключателе равен нулю, а его пара — нет; глобальная проверка тогда ложна по построению во всех legacy-Modes. Вместо неё в таких Modes проверяется состояние «механика выключена»: поток 0, fulfillment 1, запас мёртвый, цена базовая.

### Версия v7.6 (Energy Kernel v2)

9. **Статический PASS без прогона ничего не гарантирует.** v7.6 r1 пришла со всеми статическими проверками PASS и провалила все 27 Modes: движок ищет алгебраические петли только по взятым веткам `IfThenElse`, поэтому петля, живущая при `switch = 1`, невидима и для conformance, и для audit. Если исполнитель не может запускать стенд, единственная защита — наша первая итерация; закладывайте её в план как норму, а не как сбой.
10. **Сигнал цены читает сглаженное состояние, а не мгновенный спрос.** В r1 цена ресурса читала физический коэффициент нормирования, который выводится из желаемой генерации, которая выводится из спроса, который выводится из цены энергии. В модели уже есть идиома для этого — сток-сигнал (`X Energy Demand Signal`) и «воспринимаемый» дефицит; новый ценовой слой обязан её повторять.
11. **Самотесты стенда тоже проверяются.** В `structure_qa`/`conformance_qa` пять проверок возвращали строку и в ветке провала, а `expect` считает провалом только `false` — они проходили всегда, включая заведомо устаревшие ожидания (104 граничных потока, 4 пары преобразования). Исправлено в Lab v0.9.1; в новых самотестах ветка провала обязана бросать исключение или возвращать `false`.

## 9. Вариант: исполнитель-агент с доступом к репозиторию

Исполнитель — агент, который клонирует репозиторий, работает в своей ветке и пушит её в наш `origin`. Цикл целиком и шаблон выдачи — `docs/tasks/README_RU.md`; здесь обязательные правила. Для задач, затрагивающих модель, §3–§6 продолжают действовать; для задач по стенду и инфраструктуре критерии задаёт раздел «Приёмка» задания.

### 9.1 Что исполнитель получает

- задание `docs/tasks/NNN-имя/TASK_RU.md` и `scope.json` — они уже лежат в `main` до начала работы;
- короткий текст выдачи со ссылкой на задание (шаблон в `docs/tasks/README_RU.md`).

### 9.2 Правила работы в репозитории

1. **Только своя ветка** `task/NNN-имя`, созданная от текущего `main`. `main`, теги и чужие ветки не трогаются: ни push, ни удаление. Технически репозиторий это не запрещает (приватный репозиторий без защиты веток), поэтому соблюдение проверяется при каждой приёмке: `tools/check_branch.mjs` сверяет `origin/main` и теги с нашим локальным состоянием.
2. **Линейная история.** Без merge-коммитов. Если `main` ушёл вперёд: `git rebase origin/main`, пересобрать SUMS, `git push --force-with-lease` в свою ветку. Это единственный допустимый force-push.
3. **Подпись в каждом коммите — строкой `Agent: <имя>` в сообщении коммита.** Поле author не используется для атрибуции: агент, пишущий через API-коннектор, выбрать его не может, и автором окажется владелец токена. Строку в сообщении может написать любой агент, и `check_branch` проверяет её у каждого коммита ветки.
4. **Только пути из `scope.json`.** Защищённые пути (список в `docs/tasks/README_RU.md`) — только если задание явно перечислило их в `allow_protected`. Если без выхода за scope задачу не решить — остановиться и написать об этом в отчёте, а не расширять scope самому. `scope.json` в ветке не редактируется: проверка читает его из `main`.
5. **Байты артефактов.** `.gitattributes` = `* -text`: git не трогает окончания строк, поэтому их сохранность — на исполнителе. Изменённый файл сохраняет свою конвенцию: CRLF остаётся CRLF, файл без перевода строки в конце остаётся без него. Новые текстовые файлы — LF. Правка CRLF-файла инструментом, который молча меняет окончания строк (например, `sed -i` в Git Bash), — дефект поставки.
6. **Целостность** (для агента без локального git — см. 9.4). Перед каждым push: `node tools/build_sums.mjs` (пересобирает `lab/SHA256SUMS.txt` и `SHA256SUMS.txt`), затем самопроверка
   `node tools/check_branch.mjs --scope=docs/tasks/NNN-имя/scope.json --head=HEAD --base=origin/main --no-remote` → `BRANCH CHECK: PASS`.
7. **Без локальных путей и секретов** в добавленных строках: ни абсолютных путей домашних каталогов, ни токенов, ни `.npmrc` с авторизацией.
8. **Отчёт — часть поставки**: `docs/tasks/NNN-имя/REPORT_RU.md` в той же ветке (структура задаётся заданием). Отчёты стенда (`lab/output/`) в git не попадают: нужные выдержки — в отчёт или в описание PR.

### 9.3 Доработка и приёмка

- Замечания мы пишем в PR (или передаёт владелец). Исполнитель отвечает **новыми коммитами** в ту же ветку и дополняет `REPORT_RU.md` разделом «Раунд N», прежние разделы не переписывает.
- Приёмку ведём мы: `check_branch` → стенд на чистом checkout головы ветки → чтение диффа и отчёта. Принятая ветка получает наш коммит с `ACCEPTANCE_RU.md` и вливается в `main` fast-forward'ом; коммиты исполнителя сохраняются как есть.
- Guard и сборщик SUMS проверяются собственным самотестом `bash tools/selftest.sh`. Если исполнитель считает, что guard ошибается, — это замечание в отчёте с воспроизведением, а не обход.

### 9.4 Агент без локального git (только API-коннектор)

Агент, который пишет в репозиторий через API (blobs / trees / commits / refs), но не имеет локального checkout с сетью и не может запускать стенд, — это исполнитель §7, получивший право записи. Для него, в дополнение к 9.2:

1. **Самопроверка `check_branch` до push не требуется**, как и прогоны стенда. Push незавершённой ветки ничего не ломает: `main` защищает наша приёмка, а не самопроверка. Первый прогон guard'а и стенда у нас — это первый раунд, его закладываем в план как норму (урок №9).
2. **SUMS пересобираем мы**, если в `scope.json` задачи стоит `"sums_by": "reviewer"`; тогда устаревшие SUMS в ветке — предупреждение guard'а, а не провал. Без этого флага SUMS — обязанность исполнителя, как в 9.2 п. 6.
3. **Байты — на исполнителе и без локальных инструментов**: содержимое файла, отправляемое через API, должно сохранять конвенцию окончаний строк (9.2 п. 5). Guard это проверит, но исправлять придётся раундом.
4. **Отчёт обязан перечислить, что не запускалось** и чем это заменено (чтение кода, рассуждение, проверка на другой ОС). Непроверенное не выдаётся за проверенное.
5. **Входные данные, которые агент не может получить из своей среды** (бинарные файлы из внешних источников и т. п.), поставляем мы — коммитом в `main` до выдачи задания, с проверкой происхождения.

Что агент может и чего не может в своей среде, выясняется **до выдачи задания** — это та же проверка реализуемости, что и skeleton-патч (урок №1), только для исполнителя, а не для спецификации.
