# Planet v1: контракт замкнутости

**Статус:** CURRENT, решения владельца 2026-09-26 (§6). Числа «сейчас» сняты с accepted v7.7.1 r1.
**Заменяет:** раздел «Planet v1 acceptance concept» в `docs/ROADMAP.md`.

## 1. Зачем

Счётчик, который вёл проект с v7.4, дошёл до нуля и больше ничего не показывает. `open_boundaries` классифицирует все 122 граничных потока, closed-world нарушений **0**, `external_capital` = 0 с v7.5.1. Отчёт аудита сам оговаривает, что ноль «не заявка на полноту Planet v1».

При этом в модели по-прежнему много внешнего, просто этот счётчик его не видит. Он смотрит на **потоки вещества через границу**. Он не смотрит на **процессы**:
- чем они питаются (энергия);
- откуда берётся их мощность (капитал);
- кем они выполняются (труд);
- для кого производится (потребление).

Planet v1 — это набор частей. У каждой части есть свой счётчик, текущее значение и цель. Когда все цели достигнуты, планета v1 принята. «Реалистичность» здесь не утверждается. Утверждается только замкнутость на выбранном уровне абстракции.

## 2. Единица учёта: процесс

**Процесс** — поток, который создаёт физическое количество: источник `∅ → запас` в категориях добычи или преобразования. На v7.7.1 r1 в каждой колонии 7 таких процессов. Отдельно учитываются генерация (производит энергию, а не вещество) и общий транспорт.

| Процесс (колония A; B зеркальна) | Мощность | Энергия | Труд |
|---|---|---|---|
| `A Mining` (руда) | **константа** 70 | **нет** | нет |
| `A Metal Production` (плавка) | капитал (Refinery, жизненный цикл) | да, 30 на ед. | в цене |
| `A Electronics Production` | капитал (Factory, жизненный цикл) | да, 12 на ед. | в цене |
| `A Capital Goods Production` | **константа** 2 | **нет** | нет |
| `A Regolith Extraction` | **константа** 7 | **нет** | нет |
| `A Construction Materials Production` | **константа** 3 | **нет** | нет |
| `A Power Resource Extraction` | **нет предела**: спрос × запас хода | **нет** | нет |
| генерация (`A Power …`) | капитал (Generation, жизненный цикл) | — (производит энергию) | нет |
| общий транспорт | капитал (Transport, жизненный цикл, две ноги A/B) | **нет** | нет |

`A Electronics Feedstock Extraction` — старый путь: при `Intermediate Inputs Enabled = 1` он равен 0. В учёт не входит.

«Труд в цене» означает: `Labor per Unit × Wage` входит в себестоимость, но `Wage` — константа (100), и никакого ограничения по числу работников нет. Конечный спрос задан константами (`Local Base Demand` 16 и 20), потребление уходит в `∅`, населения нет.

## 3. Части контракта

Для каждой части: что считается, текущее значение, цель Planet v1, чем закрывается.

### P1. Капитал: расширение физически обеспечено — ЗАКРЫТО

- **Счётчик:** `external_capital` (`open_boundaries`).
- **Сейчас:** 0. **Цель:** 0.
- Остаётся как регрессионная проверка.

### P2. Мощность: процесс работает на капитале, а не на константе

- **Счётчик:** процессы, у которых мощность — константа или отсутствует.
- **Сейчас:** **5** на колонию (руда, оборудование, реголит, стройматериалы, энергоресурс), итого 10.
- **Цель:** 0 необъявленных. Процесс либо ведёт свою мощность через жизненный цикл капитала (kernel v2: расширение из оборудования и стройматериалов), либо внесён в явный список исключений с причиной.
- **Почему важно:** сейчас планета не может нарастить собственную промышленность оборудования и стройматериалов. Мощность 2 и 3 задана навсегда, и любой рост упирается в неё. Это потолок, которого не видно ни в одном счётчике.
- **Чем закрывается:** перенос этих отраслей на готовое ядро жизненного цикла, отрасль за отраслью. Шаблон уже есть и опробован на 4 секторах.

### P3. Энергия: каждый процесс объявляет потребление энергии

- **Счётчик:** процессы без объявленной энергетической роли.
- **Сейчас:** **5 из 7** процессов не потребляют энергию (всё, кроме плавки и электроники), плюс транспорт: 6 на колонию, если считать транспорт.
- **Цель:** 0 необъявленных. Роль — одно из двух:
  - `requests_energy`: запрос входит в `Total Requested Energy`, выпуск ограничен распределением энергии;
  - `none` с причиной, например «добыча энергоресурса учтена как КПД генерации».
- **Чем закрывается:** ROADMAP-шаг «стройматериалы с энергией» — первый. Дальше руда, реголит, оборудование, транспорт. Главный риск — аллокатор: урок v7.4 про петли. Теперь его ловит аудит петель ещё на skeleton.

### P4. Ресурсная база: добыча ограничена недрами планеты

- **Счётчик:** добывающие процессы без стока недр.
- **Сейчас:** **3** на колонию (руда, реголит, энергоресурс), недра бесконечны: добыча идёт из `∅` без запаса.
- **Цель v1:** 0. Каждый добывающий процесс читает свой сток недр (`X <Resource> Deposit`), начальное значение которого — именованный параметр (`X <Resource> Deposit Initial`). Добыча ограничена стоком точно (`Min`, а не мягким насыщением): пока недр хватает, ряды старых Modes не меняются, и регрессия остаётся точной. На горизонте 1080 дней значения могут быть заведомо большими — поведение от этого не меняется, но зависимость от планеты становится структурной.
- **Цель v8:** начальный запас недр выводится из параметров формирования планеты (шаблон планеты), а не задаётся числом. В v1 меняется только источник числа.
- `infinite_deposit` как объявление в v1 **не допускается**.

### P5. Труд: объявлен, без ограничения

- **Счётчик:** процессы без объявленной трудоёмкости.
- **Сейчас:** 2 объявлены (плавка, электроника: труд только в себестоимости, `Wage` — константа); остальные 5 процессов, генерация и транспорт труд не упоминают.
- **Цель v1:** 0 необъявленных. Каждый процесс объявляет `labor_intensity` (может быть 0 с причиной); ограничения по пулу рабочей силы в v1 **нет**.
- **Открытый пункт (приёмка задачи 011).** Сейчас `labor: declared` проверяется только так: «параметр трудоёмкости существует и его кто-то читает». Связь параметра с процессом не проверяется: декларация «руда: труд = `Labor per Metal`» проходит. Строго проверить это нельзя, пока труд есть только в себестоимости. Шаг модели для P5 вводит явную переменную `X <Process> Labor Requirement = выпуск × трудоёмкость`, и `labor: declared` будет требовать, чтобы эта переменная читала выход процесса и параметр трудоёмкости (путь ≤ `max_hops`). До этого шага счётчик P5 доверяет декларации.
- **Planet v2:** население, пул труда, ограничение выпуска трудом (решение 2026-09-26: население — рано).

### P6. Потребление: внешний драйвер, объявленный явно

- **Сейчас:** конечный спрос — константы (`Local Base Demand` 16 / 20) плюс эластичность по цене; потребление уходит в `∅` (`final_consumption`, closed-world «да»).
- **Цель v1:** спрос объявлен как **внешний драйвер** — явная категория контракта с перечнем параметров, а не незаметная константа. Это единственная разрешённая «внешность» Planet v1.
- **Planet v2:** спрос из корзины жизнеобеспечения населения.

### P7. Воспроизводимость — ЗАКРЫТО, с оговоркой

- Детерминизм, точная регрессия, аудит петель, закреплённый движок, эталон канонической платформы — есть.
- **Оговорка:** точные числа воспроизводятся только на Windows. Для «публичного Planet v1» нужна независимость от платформы (ROADMAP, открытый технический пункт). Для внутреннего v1 оговорка допустима.

## 4. Как это встраивается в стенд

Предлагаю сделать это по образцу `open_boundaries`, как новый плагин validation `planet_closure`: декларация плюс аудит только по именам и топологии.

```json
{
  "type": "planet_closure",
  "enforce": "report",
  "processes": [
    { "flow": "* Mining", "capacity": "constant", "energy": "none", "labor": "none",
      "reason": "v7.4 primary extraction; see P2/P3" },
    { "flow": "* Metal Production", "capacity": "kernel:Refinery", "energy": "requests:* Metal Requested Energy",
      "labor": "cost_only" }
  ],
  "exceptions": []
}
```

- Аудит сверяет декларацию с моделью. Каждый поток-источник в категориях добычи или преобразования должен быть объявлен процессом. Если объявлено `requests:X`, то `X` действительно входит в `Total Requested Energy`, а выпуск читает fulfillment. Если объявлено `kernel:S`, то мощность — это сток ядра `S`. Если объявлено `constant`, то это действительно константа.
- Результат — счётчики P2–P5 и перечень процессов, которые не дотягивают до цели. Режимы, как у `open_boundaries`: `report` (только метр) → `classify` (необъявленный процесс = FAIL) → `planet_v1` (любое отставание от цели = FAIL) → `planet_strict` (плюс 0 исключений).
- Модель не меняется: на v7.7.1 декларация фиксирует текущее состояние, а числа берутся из таблицы §2.

**Исключения (решение 2026-09-26: в v1 допускаются).** `capacity: constant` и `energy: none` допустимы с обязательной `reason`. Правила, которые сохраняют обратимость:

- счётчик показывает исключения **отдельной строкой** — «0 необъявленных, N исключений», число не прячется;
- мощность-константа с причиной не может быть опорой для других процессов: ни одна формула не делает вывод из того, что мощность неизменна. Замена константы на сток ядра остаётся локальной;
- снятие исключения — обычный шаг модели (skeleton → `loops` → задание → приёмка); шаблон ядра капитала и энергетический запрос его стоимость не повышают;
- режим `planet_strict` (0 исключений) заложен в плагин сразу; ужесточение — смена режима, а не переписывание контракта.

## 5. Порядок работ (предложение)

1. **Решения владельца** по вопросам ниже; черновик становится `docs/PLANET_V1_CONTRACT.md`, раздел ROADMAP заменяется ссылкой.
2. **Задача для агента (стенд):** плагин `planet_closure` в режиме `report`, декларация для v7.7.1, самотесты на мутациях, счётчики в отчёте `STRUCTURE_AUDIT`. Это инфраструктура по образцу задачи 010.
3. **Модель, по одному шагу, каждый со своим счётчиком:**
   - стройматериалы с энергией (P3: 5 → 4);
   - стройматериалы на капитале (P2: 5 → 4);
   - затем руда, реголит, оборудование, транспорт, в порядке, который покажет счётчик.

   Каждый шаг идёт по обычному циклу: skeleton → `loops` → задание → приёмка.
4. P4 (стоки недр), P5 (объявление труда), P6 (объявление драйвера спроса) — шаги модели и декларации в том же порядке по счётчику; затем режим `planet_v1`.

## 6. Решения владельца (2026-09-26)

1. **Население в Planet v1 — нет.** Рано. Труд в v1 только объявляется (P5), спрос — явный внешний драйвер (P6); население, пул труда и корзина жизнеобеспечения — Planet v2.
2. **Недра — зависимость от планеты.** В v1 — конечный сток недр из именованного параметра, точное ограничение (P4); в v8 параметр выводится из формирования планеты. Объявление «бесконечно» не используется.
3. **Исключения в P2/P3 — допускаются** в v1, с причиной и отдельным счётом; обратимость обеспечивают правила §4, ужесточение — режим `planet_strict`.
4. **Порядок:** сначала задача на плагин `planet_closure` (режим `report`), затем шаги модели под счётчиком; первый — стройматериалы с энергией.
