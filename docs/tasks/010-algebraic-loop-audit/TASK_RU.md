# Задание 010 — статический аудит алгебраических петель с учётом переключателей

Ветка: `task/010-algebraic-loop-audit` · Scope: `scope.json` рядом · Правила: контракт §9, §9.2 п. 9 (контрольные точки и журнал), §9.4 · Порядок работы: `docs/tasks/README_RU.md`

## 1. Зачем

Движок `simulation@9.0.0` находит алгебраическую петлю только на прогоне и только по **взятым** веткам `IfThenElse`. Петля, которая существует лишь при каком-то значении переключателя, для статических проверок стенда (conformance, structure audit) невидима. Так провалились две поставки:

- **001 r1**: спрос на вход строился от фактического потребления; Modes 17–20 (`Intermediate Inputs Enabled = 1`) не стартовали;
- **v7.6 r1**: цена ресурса читала мгновенное нормирование; Modes 25–26 (`Power Resource Enabled = 1`) упали с `Circular equation loop`.

Стенд прогоняет только те комбинации переключателей, которые заданы в сценариях. Сейчас переключателей 7, то есть 128 комбинаций, а Modes 32. Задача — аудит, который до всякой симуляции проверяет все комбинации и на каждой петле печатает её путь.

Прототип уже есть и даёт эталонные числа: `reference/loops_prototype.mjs`. Он **не нормативен**: модуль стенда можно написать по-другому, но вердикты из §4 он обязан воспроизвести.

## 2. Что проверяется

1. **Граф одного шага.** Узлы — `VARIABLE` и `FLOW`. `STOCK` читается с прошлого шага и разрывает граф. Ребро `X → Y` есть, если в формуле `Y` встречается `[X]`. Ребро строится по ссылкам в формулах, а не по `LINK`: связи на схеме могут существовать без ссылки в формуле.
2. **Переключатель** — переменная, у которой одновременно:
   - значение в модели — литерал `0` или `1`;
   - она задаётся хотя бы в одном сценарии;
   - все её значения в сценариях равны `0` или `1`.

   Правило не зависит от имён. На v7.7.1 оно даёт ровно 7 переключателей `* Enabled`. `Timed Test Mode` переключателем не считается: его значения 0…31.
3. **Отсечение ветвей.** В `IfThenElse(c, a, b)` условие `c` решается, только если оно ссылается лишь на подставленные переменные и литералы (операторы `= < > <= >=`, скобки). Тогда остаётся взятая ветка. Иначе остаются обе. Условия от состояния модели (`[Inventory] < …`, `Days() >= …`) всегда «возможны». Такой режим консервативен: возможны лишние предупреждения, но петля не будет пропущена. Вложенные `IfThenElse` обрабатываются изнутри наружу.
4. **Два уровня.**
   - **Комбинации:** все 2^N сочетаний переключателей, остальные переменные не подставляются.
   - **Modes:** для каждого сценария подставляются все его значения (включая `Timed Test Mode`, по умолчанию берутся значения модели). Итог — список Modes с петлёй. Это прогноз того, где движок откажется считать.
5. **Петля** — сильно связная компонента (Тарьян) размером больше 1 или узел со ссылкой на себя. Одинаковые компоненты из разных комбинаций сливаются в одну находку: состав, размер, число комбинаций и первая из них. В отчёт идёт **кратчайший цикл** внутри компоненты: именно его нужно разорвать. Компонента из 163 элементов человеку ничего не говорит.

## 3. Что сделать

### 3.1 Модуль `lab/src/loop_audit.js`

- `auditAlgebraicLoops(raw)` возвращает объект `{ type: 'algebraic_loops', status, switches, combinations, combinationsWithLoops, loops[], modesWithLoops[] }`. Каждый элемент `loops[]` содержит: `size`, `members`, `shortestCycle` (путь), `combinations` (число), `example` (включённые переключатели первой комбинации).
- Детерминированность: одинаковый вход даёт побайтно одинаковый JSON-отчёт. Порядок обхода фиксирован порядком элементов модели; никаких `Date`, случайности и порядка хэш-таблиц в результате.
- Парсер формул не должен молча пропускать то, чего не понял. Несбалансированные скобки и незакрытый `IfThenElse` дают `FAIL` с именем элемента.
- Время на принятой модели — в отчёт (прототип укладывается примерно в 0,4 с).

### 3.2 Встраивание

- `runStructureAudits` (`lab/src/structure_audit.js`) всегда включает `algebraicLoops`. Аудит не зависит от плагинов validation и validation не меняет.
- `status: FAIL`, если петля есть **хотя бы в одной комбинации**, даже если ни один Mode её не задаёт: весь смысл аудита — в скрытых петлях.
- Петли попадают в `structureAuditErrors`. Тогда `CHECK_CANDIDATE`/`compare` с петлёй дают `NOT_COMPARED` без симуляции, как уже делают другие структурные аудиты.
- Вывод: `printStructureAudits`, `structure-audit.md`/`.json` (`audit_run.js`), раздел в отчёте `RUN_LAB` (`report.js`). Выводятся число переключателей, число комбинаций, число комбинаций с петлями и Modes с петлёй. Для каждой находки — размер, число комбинаций, пример и кратчайший цикл.
- Новая команда `node src/cli.js loops <model.json> [--out=DIR]`: без validation, код выхода 1 при петлях. Она нужна нам на этапе skeleton, до выдачи задания.
- Существующие проверки `open_boundaries` и `colony_symmetry` не меняются. Если какой-то кейс `structure_qa.js` опирался на статус `SKIPPED` при отсутствии плагинов, поведение нужно согласовать и описать в отчёте.
