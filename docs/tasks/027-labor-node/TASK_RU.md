# Задание 027 — тип узла `labor`: потребность в труде каждого процесса, с автоматизацией с самого начала

Ветка: `task/027-labor-node` · Scope: `scope.json` рядом · Правила: контракт 1.9 §9, §9.2 п. 9 (контрольные точки и журнал), §9.4 · Порядок работы: `docs/tasks/README_RU.md`

## 1. Зачем

Planet v1 **P5** (`docs/PLANET_V1_CONTRACT_RU.md`, решения владельца от 2026-10-03). Каждый процесс объявляет трудоёмкость, ограничения по пулу рабочей силы в v1 нет.

Сейчас:
- объявлены 4 экземпляра из 17: плавка и электроника, A/B;
- их труд есть только в себестоимости;
- открытый пункт приёмки 011: `labor: declared` проверяется лишь как «параметр трудоёмкости существует и его кто-то читает», связь с процессом не проверяется.

Решения владельца:
1. **Потребность в труде сразу с автоматизацией.** `X P Labor Requirement = выпуск × трудоёмкость × коэффициент автоматизации`. Коэффициент `= 1 − (1 − h) × (1 − (1 − a)^k)`: алгебраически это `h + (1 − h)(1 − a)^k`, но при `a = 0` первая форма даёт **ровно 1** при любом `h`, а вторая — не всегда (`0.07 + 0.93`). Уровень автоматизации `a` — именованный параметр процесса, без динамики. Динамика (автоматизация как состояние капитала) — в v2, вместе с населением.
2. **Автоматизация на старте 0.** Коэффициент 1, ни один прежний ряд не меняется — **переключатель не нужен**.
3. **Трудоёмкости** (человеко-дни на единицу, масштаб плавки 0.1): руда 0.05, оборудование 2, реголит 0.2, стройматериалы 0.3, энергоресурс 0.002, генерация 0.001 на единицу энергии, транспорт 0.1 на единицу груза; плавка 0.1 и электроника 0.05 — существующие. `h` = 0.05, `k` = 1.
4. **Себестоимость плавки и электроники читает трудоёмкость × коэффициент.** При коэффициенте 1 это побайтно прежние значения; позже рост автоматизации сразу снизит себестоимость.

Одна механика повторяется 17 раз (8 процессов × 2 колонии + общий транспорт) — это работа генератора узлов. Задача:
- тип узла `labor` (Lab v0.9.15);
- строгая проверка труда в `planet_closure`;
- плагин validation `labor`.

**Модель, validation и policy не меняются.** Первым применением станет задача по модели v7.7.10 (028); после неё `planet_closure` можно переводить в режим `planet_v1`.

## 2. Узел `labor`

### 2.1 Декларация (строгая схема; незнакомое поле — ошибка с путём)

```json
{
  "type": "labor", "version": 1, "colonies": ["A", "B"],
  "automation": { "min_human_share": { "name": "Minimum Human Labor Share", "value": 0.05 },
                  "exponent": { "name": "Automation Labor Exponent", "value": 1 } },
  "processes": [
    { "process": "Smelting", "output": "{C} Metal Production", "intensity": { "existing": "{C} Labor per Metal" },
      "automation": { "A": 0, "B": 0 }, "cost": ["{C} Metal Unit Cost"], "planet_process": "smelting" },
    { "process": "Mining", "output": "{C} Mining", "intensity": { "value": 0.05 },
      "automation": { "A": 0, "B": 0 }, "planet_process": "mining" },
    { "process": "Transport", "scope": "shared", "output": "Capacity Limited Total Transport Load",
      "intensity": { "value": 0.1 }, "automation": { "shared": 0 }, "planet_process": "transport" }
  ]
}
```

Правила декларации:
- `intensity` — ровно одно из `existing` (имя параметра в базе) или `value` (конечное число > 0);
- `automation` — ключи ровно по `colonies`, у `scope: "shared"` — ровно `shared`; значения в [0, 1];
- `min_human_share` в (0, 1); `exponent` > 0;
- `cost` необязателен; каждая формула в нём обязана читать параметр трудоёмкости, иначе ошибка с именем;
- `output` с `{C}` недопустим у `shared`, без `{C}` — у колониального процесса;
- имя, которое генератор создал бы, уже есть в базе — ошибка с именем.

### 2.2 Раскрытие (имена и формулы — как в прототипе; P — процесс, X — колония; у `shared` префикса колонии нет)

**Общие параметры:** `h`, `k` — имена из декларации.

**На процесс:**
- трудоёмкость — существующий параметр, либо новый `X P Labor per Unit`;
- `X P Automation Level` = значение из декларации;
- `X P Automation Factor = 1 - (1 - [h]) * (1 - (1 - [X P Automation Level]) ^ [k])`;
- `X P Labor Requirement = [output] * [intensity] * [X P Automation Factor]`;
- в каждой формуле из `cost` каждая ссылка `[intensity]` заменяется на `([intensity] * [X P Automation Factor])`.

**Итоги:** `X Total Labor Requirement` — сумма колониальных процессов; `Shared Labor Requirement` — сумма общих.

**Связи:** на каждую ссылку новых и заменённых формул, без дублей.

Потоков узел не создаёт; переключателя нет.

### 2.3 Фрагменты validation и слияние

- `planet_closure`: у процесса `planet_process` ставится `labor: { kind: "declared", intensity, requirement: "{C} P Labor Requirement" }` (у `shared` — без `{C}`). Заглушка `undeclared` заменяется. Объявленная декларация без `requirement` (плавка, электроника в v7.7.9) тоже заменяется: фрагмент содержательнее; при расхождении `intensity` — конфликт.
- **Новый плагин `labor`**: `abs_tol`, `min_human_share` (имя параметра), `instances` — по экземпляру `{ name, output, intensity, automation_level, automation_factor, requirement }`.
- Повторное слияние идемпотентно; если ничего не меняется — файл копируется побайтно.

### 2.4 Проверки

1. **`planet_closure`, поле `labor.requirement`.**
   - `requirement` — VARIABLE и читает **напрямую** выход процесса и параметр трудоёмкости; нарушение — ошибка процесса с именем.
   - В режимах `planet_v1` и `planet_strict` декларация `declared` **без** `requirement` — провал режима (`P5: labor declared without a requirement variable`). Это закрывает открытый пункт приёмки 011.
   - В режиме `report` без `requirement` — прежнее поведение, побайтно.
   - Схема плагина знает поле.
2. **Плагин `labor`.**
   - **Статика** (в этапе conformance, HARD): типы ролей; `requirement` читает `output`, `intensity`, `automation_factor`; `automation_factor` читает `automation_level` и `min_human_share`.
   - **Прогон**:
     - `automation_level` в [0, 1];
     - `automation_factor` в [`min_human_share`, 1];
     - `requirement` ≥ 0;
     - `requirement` = `output × intensity × automation_factor` с относительным допуском `abs_tol` (новый вид проверки — произведение рядов; добавить в `checks.js` как функцию плагина, не как новый тип проверки языка).
