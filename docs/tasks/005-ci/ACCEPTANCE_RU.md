## Находка: стенд не воспроизводится бит-в-бит между ОС

Сравнение `report.json` полного прогона на Linux (артефакт run `36157360135`) с нашим Windows-прогоном той же модели v7.6.1 r1, тот же Node 24.11.1, тот же `simulation` 9.0.0:

| Modes | Linux против Windows (значения, которые выводят проверки) |
|---|---|
| 0–16 | совпадают точно |
| 17, 18, 20, 21, 22 | расходятся в 14–15-м знаке (максимум 7·10⁻¹⁴ относительно) |
| 23 | до 6.6·10⁻⁴ |
| **19** | **до 4.35 %** (например, A metal input demand на день 1080: 9.499 против 9.931) |
| 24–26 | в проверяемых значениях совпадают |

Все проверки проходят на обеих ОС, но значения не тождественны. Modes 0–16 — ровно та область, где делалась золотая сверка браузер ↔ Windows (v7.3); расхождение начинается с Mode 17, то есть с механики промежуточных входов v7.4. Вероятная причина — операция, которую движок на разных платформах вычисляет с разницей в последнем бите; динамика Mode 19 усиливает её до процентов.

**Что это значит для проекта.**

- Точная регрессия (`maxAbs = 0`) остаётся строгой **в пределах одной платформы**: `CHECK_CANDIDATE` и `COMPARE_MODELS` считают обе модели на одной машине, поэтому их вердикты на Linux так же верны, как на Windows.
- Сравнивать числа **между** платформами бит-в-бит нельзя. Принятые эталоны получены на Windows; CI на Linux — подсказка, а не замена приёмки (и так было записано в задании).
- Золотая сверка с браузером для Modes 17+ никогда не делалась — браузер тоже может расходиться.

Записано в `lab/ENGINE_PIN.md`. Поиск первопричины — кандидат в следующее задание (матрица ubuntu + windows в Actions даёт агенту средство для этого).
