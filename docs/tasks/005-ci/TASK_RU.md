# Задание 005 — CI на GitHub Actions: петля обратной связи для веток задач

Ветка: `task/005-ci` · Scope: `scope.json` рядом · Правила: `docs/CONTRACTOR_DELIVERY_CONTRACT_RU.md` §9 и §9.4 · Порядок работы: `docs/tasks/README_RU.md`

## 0. Сначала — проверка среды (обязательно, до любой работы)

Задание имеет смысл, только если твоя среда умеет две вещи. Проверь обе и **первым коммитом** в ветку положи `REPORT_RU.md` с разделом «Среда» и ответом на каждый пункт:

1. **Создавать и изменять файлы в `.github/workflows/`.** GitHub отвергает такие изменения, если у токена нет права `workflow`, — даже когда остальные файлы пишутся. Проверка: создать в своей ветке `.github/workflows/ci.yml` с минимальным workflow (например, один шаг `echo`).
2. **Читать результаты Actions**: список запусков для своей ветки, статус каждого job и **логи** шагов (не только зелёный/красный).

Если хоть одно «нет» — остановись после этого коммита и напиши, чего не хватает. Обходить не нужно: без п. 1 задачу выполнить нельзя, без п. 2 теряется её смысл.

## 1. Зачем

Задачу 004 ты сделал вслепую: код, который ни разу не запускался, прошёл стенд с первого раунда, но каждая проверка шла через нас. CI на push в ветку `task/*` даёт тебе собственную петлю: запушил → Actions прогнали guard и самотесты → ты читаешь результат и исправляешь, не дожидаясь нас. Это условие для следующих задач по модели, где раундов больше.

Второй эффект — первая проверка стенда **на Linux**. До сих пор он запускался только на Windows. Движок детерминирован, но это никто не проверял на другой ОС.

## 2. Что сделать

### 2.1 Workflow на push — `.github/workflows/ci.yml`

Триггеры: `push` в `main` и в `task/**`; `workflow_dispatch`. Раннер `ubuntu-latest`. Параллельные запуски одной ветки отменяют предыдущий (`concurrency`, `cancel-in-progress`).

Jobs (каждый — отдельный статус, чтобы по списку было видно, что упало):

| Job | Когда | Что делает |
|---|---|---|
| `guard` | ветки `task/NNN-…` | `node tools/check_branch.mjs --scope=<scope> --head=HEAD --base=origin/main --no-remote`. `<scope>` находится **по номеру** `NNN` из имени ветки: ровно один файл `docs/tasks/NNN-*/scope.json` в `origin/main` (так ветка `task/005-ci-probe` проверяется по scope задачи 005). Нет такого файла или их несколько — job падает с понятным сообщением. Нужна полная история (`fetch-depth: 0`) и `origin/main`. |
| `integrity` | `main` | `node tools/build_sums.mjs --check` |
| `tools-selftest` | всегда | `bash tools/selftest.sh` |
| `bench-selftests` | всегда | установка стенда **офлайн из `lab/vendor/`** теми же шагами, что в `lab/INSTALL.cmd` (временный кэш из tarball'ов, `npm ci --offline`), затем самотесты стенда `node`-командами из соответствующих `.cmd`: QA, STRUCTURE, CONFORMANCE, POLICY, COMPARE и SELF_TEST (Modes 0, 12). |

Требования:

- **Node — ровно `24.11.1`** (на ней принята эталонная работа стенда), не «24.x».
- **Действия (`uses:`) закреплены полным SHA коммита** с комментарием-версией, например `actions/checkout@<40 знаков SHA> # v4.x.y`. Теги двигаются, SHA — нет.
- `permissions: contents: read` на уровне workflow. Никаких секретов.
- Без кэширования `node_modules` между запусками: установка из `vendor/` и так быстрая, а кэш — ещё один источник невоспроизводимости.
- Push-запуск целиком укладывается примерно в 5 минут: минуты Actions в приватном репозитории ограничены.

### 2.2 Полный прогон по требованию — `.github/workflows/bench-full.yml`

Только `workflow_dispatch` (с входом `ref`, по умолчанию `main`). Та же установка, затем `node --expose-gc src/cli.js lab --input=input` (все 27 Modes) и `node --expose-gc src/cli.js policy --modes=all` (принятая модель против себя). Отчёты `lab/output/` — артефактом запуска. Ожидаемый итог на `main`: `OVERALL: PASS` и `COMPARISON RESULT: BYTE_IDENTICAL` / `POLICY RESULT: PASS`. Запусти его сам на своей ветке хотя бы один раз.

### 2.3 Переносимость стенда

Если самотесты или прогон падают на Linux из-за самого стенда (пути, регистр имён файлов, окончания строк и т. п.), а не из-за workflow, — исправь это в `lab/src/` так, чтобы на Windows всё осталось как было. Каждое такое исправление: что падало (выдержка из лога Actions), почему, что изменено. Любое изменение `lab/` — это Lab **v0.9.4** (баннеры, `package.json`/lock, `CHANGELOG.md`, `docs/HISTORY_RU.md`), как в задаче 004. Если стенд переносим без правок — версия не меняется.

Поведение проверок стенда не менять. Результаты моделирования на Linux обязаны совпасть с Windows; если не совпадают — не «чинить», а остановиться и описать расхождение в отчёте: это находка, а не дефект задачи.

### 2.4 Документация

- Корневой `README.md` — раздел «CI»: что запускается на push, что по кнопке, где смотреть результаты, и что CI — **подсказка, а не приёмка** (см. п. 4).
- `lab/README_RU.md` — короткая ссылка на CI в разделе установки.

`docs/tasks/README_RU.md` и контракт обновим мы при приёмке.

### 2.5 Чего не делать

- Не менять `tools/`, `lab/vendor/`, модель, validation, policy и другие защищённые пути (список — `docs/tasks/README_RU.md`); `.github/` для этой задачи разрешён.
- Не добавлять зависимостей, не использовать сторонние (не GitHub) actions без необходимости; если понадобятся — обоснуй в отчёте.
- Не трогать `main`, теги и чужие ветки. Для экспериментов с workflow достаточно своей ветки.
- SHA256SUMS не пересобирать — `sums_by: reviewer`.

## 3. Приёмка

| # | Критерий | Кто | Как проверяется |
|---|---|---|---|
| B0 | Среда | исполнитель | раздел «Среда» в отчёте, первым коммитом |
| B1 | Guard | мы | `check_branch` → PASS (SUMS — предупреждения) |
| B2 | CI зелёный на самой ветке | исполнитель → мы | ссылки на запуски в отчёте; мы открываем их |
| B3 | CI падает, когда должен | мы | мы пушим временную ветку `task/005-ci-probe` с нарушением (например, CRLF→LF в `lab/package.json`) — job `guard` обязан упасть, остальное — пройти; ветку удаляем |
| B4 | Полный прогон | исполнитель → мы | запуск `bench-full` на ветке: 27/27 PASS, `BYTE_IDENTICAL`, `POLICY PASS` |
| B5 | Linux = Windows | мы | отчёты `bench-full` сравниваем с нашим Windows-прогоном: итоги проверок и число рядов по каждому Mode совпадают |
| B6 | Бережливость | мы | push-запуск ≲ 5 мин; Node 24.11.1; действия по SHA; `contents: read` |
| B7 | Стенд на Windows не изменился | мы | если менялся `lab/`: самотесты и `RUN_LAB` на Windows — прежние результаты |

## 4. Почему CI — подсказка, а не приёмка

Workflow исполняется из той ветки, которую проверяет: исполнитель может изменить его вместе с поставкой. Поэтому `.github/` защищён guard'ом для всех следующих задач, а решение о приёмке по-прежнему принимается по нашему локальному прогону. CI экономит раунды, но не заменяет их.
