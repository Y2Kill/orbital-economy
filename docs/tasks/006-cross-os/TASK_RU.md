# Задание 006 — почему стенд на Linux и Windows считает по-разному

Ветка: `task/006-cross-os` · Scope: `scope.json` рядом · Правила: контракт §9 и §9.4 · Порядок работы: `docs/tasks/README_RU.md` (шаг 4a — CI)

## 1. Что известно

При приёмке задачи 005 мы сравнили твой полный прогон на Linux (Actions, run `36157360135`) с нашим прогоном на Windows. Модель одна (v7.6.1 r1, `16e8ca6c…`), движок один (`simulation` 9.0.0 из `lab/vendor/`), Node один (24.11.1). Все 3601 проверка проходят на обеих ОС, но **значения**, которые выводят проверки, совпадают не везде:

| Modes | Linux против Windows |
|---|---|
| 0–16 | совпадают точно |
| 17, 18, 20, 21, 22 | расходятся в 14–15-м знаке (≤ 7·10⁻¹⁴ относительно) |
| 23 | до 6.6·10⁻⁴ |
| 19 | до 4.35 % (A metal input demand на день 1080: Windows 9.499, Linux 9.931) |
| 24–26 | в проверяемых значениях совпадают (ряды целиком никто не сравнивал) |

Modes 0–16 — область, где когда-то делалась золотая сверка браузер ↔ Windows; с Mode 17 начинается механика промежуточных входов v7.4. Подробности — `docs/tasks/005-ci/ACCEPTANCE_RU.md`, вывод для проекта — `lab/ENGINE_PIN.md`.

Мы **не знаем**, что именно расходится: ОС (разные системные библиотеки), процессор (разные наборы инструкций у машин) или что-то в самом стенде. Отличить одно от другого — часть задачи.

Для ориентира — функции в формулах модели: `IfThenElse` 291, возведение в степень `^` 198, `Max` 11, `Min` 4, `Days` 3. Это опись, а не подсказка.

## 2. Что сделать

### 2.1 Выгрузка рядов с точностью до бита — `lab/src/`, команда CLI

Новая команда, например `node src/cli.js series [model.json] [--modes=all] [--out=DIR]`:

- для каждого Mode и каждого ряда — SHA-256 от байтов значений (`Float64Array`, little-endian) по всей временной оси, плюс SHA-256 временной оси;
- итоговый JSON: Mode → ряд → хеш, и общий хеш на Mode;
- по флагу (например, `--dump=MODE`) — полная выгрузка одного Mode со значениями в шестнадцатеричном виде IEEE-754, чтобы можно было найти **первый** шаг и **первый** ряд, где значения разошлись;
- команда только читает модель и пишет в `--out`; поведение остальных команд стенда не меняется.

Это Lab **v0.9.4** (баннеры, `package.json`/lock, `CHANGELOG.md`, `docs/HISTORY_RU.md`, самотест для новой команды в `lab/src/qa.js` — провал обязан быть провалом, контракт §8 п. 11).

### 2.2 Прогон на двух ОС — `.github/workflows/cross-os.yml`

Только `workflow_dispatch` (вход `ref`, по умолчанию `main`; вход `modes`, по умолчанию `all`). Матрица `ubuntu-latest` и `windows-latest`, Node 24.11.1, установка стенда офлайн из `lab/vendor/`, затем команда из 2.1; результат — артефактом. Последний job сравнивает оба результата и печатает в лог: какие Modes совпали целиком, какие нет, и для каждого расходящегося Mode — первый ряд и первый шаг времени расхождения, оба значения в hex.

В лог каждого job — сведения о машине: ОС и её версия, модель процессора, версия Node.

Требования те же, что в 005: действия закреплены по SHA, `permissions: contents: read`, без секретов, без кэша `node_modules`, `timeout-minutes` у каждого job. Windows-минуты считаются вдвое — не запускай полный прогон больше, чем нужно.

### 2.3 Первопричина

1. По первому расхождению (самый ранний шаг времени в самом раннем расходящемся Mode) найди примитив модели и его формулу.
2. Сведи расхождение к **минимальному воспроизведению**: отдельный маленький JS-файл (без модели и без стенда, только нужная операция с конкретными аргументами), который на `ubuntu-latest` и `windows-latest` печатает разные биты. Файл — в `docs/tasks/006-cross-os/repro/`; `cross-os.yml` прогоняет его в той же матрице — это доказательство.
3. Объясни, почему Modes 0–16 не задеты, а 17+ задеты: какое условие включает проблемную операцию или её проблемные аргументы.
4. Раздели гипотезы «ОС» и «процессор», насколько позволяют раннеры: если у разных раннеров разные процессоры, скажи это; если нужна третья точка (наш Windows-ПК), скажи, что именно нам запустить.

### 2.4 Рекомендация — только текст

Варианты, что с этим делать проекту, с плюсами и минусами. Например: переформулировать место в модели так, чтобы результат не зависел от платформы; признать эталон привязанным к одной платформе; что-то ещё. **Ничего из этого не внедрять**: модель, validation, движок и `lab/vendor/` в этой задаче не меняются.
