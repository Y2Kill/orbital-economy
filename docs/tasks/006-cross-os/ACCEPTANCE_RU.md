# Приёмка задания 006 — почему стенд на Linux и Windows считает по-разному

**Решение:** ПРИНЯТО 2026-09-25 с первого раунда, с одной поправкой к отчёту (ниже). Исполнитель — GPT-5.6 Sol (agent), API-коннектор + собственная петля через Actions (CI и матрица `cross-os`). Работа шла в две сессии: первая оборвалась после 5 коммитов и 11 запусков Actions, вторая, начатая без нашей подсказки, довела задачу до конца (всего 12 коммитов).

## Ответ задачи

**Причина — `Math.pow` в Node 24.11.1 на Windows и на Linux округляет по-разному.** Одинаковые до бита аргументы дают соседние double:

```text
Math.pow(0x401368263c9d9065, 0.125)      base ≈ 4.8517083617372
точное значение  1.218251166555524789017710654543…
Windows          0x3ff37df4ef6ab79d   ошибка 0.499 ULP  — округлено верно
Linux            0x3ff37df4ef6ab79e   ошибка 0.501 ULP
```

Точное значение лежит почти ровно посередине между двумя double; обычные математические библиотеки гарантируют ошибку < 1 ULP, а не корректное округление, — обе ОС в пределах этой гарантии. Оператор `^` в формулах модели движок `simulation` 9.0.0 исполняет как `Math.pow`; в модели 198 таких выражений, в том числе сглаженное насыщение `x / (1 + (x/cap)^8)^0.125` в темпах добычи и плавки.

**ОС, а не процессор** — установлено на трёх машинах:

| Машина | ОС | Процессор | `Math.pow` из воспроизведения | Хеши рядов Modes 0, 17, 19 |
|---|---|---|---|---|
| windows-latest | Windows Server 2025 | AMD EPYC 9V74 / 7763 | `…b79d` | = нашего ПК |
| наш ПК | Windows 10 Pro | Intel i7-9750H | `…b79d` | = windows-latest |
| ubuntu-latest | Ubuntu, ядро 6.17 azure | AMD EPYC 7763 | `…b79e` | другие |

Один и тот же процессор (EPYC 7763 на обоих раннерах в запуске воспроизведения) даёт разные биты на разных ОС; разные процессоры на одной ОС — одинаковые.

**Масштаб.** Побитово различаются ряды во **всех** 27 Modes (Mode 0: 421 ряд из 1004), первое расхождение — Mode 0, шаг 90 (день 22.5), `A Desired Generation`. Граница «Modes 0–16 совпадают, 17+ нет» из задачи 005 была артефактом наблюдения: там сравнивались только значения, которые печатают проверки. Механика Modes 17+ меняет не наличие проблемной операции, а то, как сильно её 1 ULP доходит до проверяемых значений (в Mode 19 — до 4.35 %).

## Поправка к отчёту исполнителя

Отчёт (разделы 3.1, 3.3) объясняет распространение через «промежуточные стадии RK4». Модель использует **RK1** (`"algorithm": "RK1"` в ModelJSON, `dt = 0.25`) — промежуточных стадий Рунге–Кутты нет. На вывод это не влияет: воспроизведение автономно, а наблюдаемые факты (номера вызовов `Math.pow`, первый вызов с одинаковыми аргументами и разным результатом, дальнейшее расхождение аргументов) от названия метода не зависят; неверно только их объяснение словами «RK4». Отчёт оставлен как поставлен, поправка — здесь.
