## 1. Зачем

Стенд Orbital Economy Lab зависит от двух npm-пакетов: `simulation@9.0.0` (движок, AGPL) и `csv-parse@5.6.0` (MIT). Проект держится на точной воспроизводимости (`maxAbs = 0` между версиями модели), движок заморожен (`lab/ENGINE_PIN.md`). Две проблемы:

1. **Воспроизводимость зависит от реестра npm.** `lab/INSTALL.cmd` скачивает пакеты при каждой установке. Если пакет снимут с публикации или реестр будет недоступен, стенд не собрать.
2. **Пин объявлен, но не обеспечен.** `INSTALL.cmd` вызывает `npm install`, который вправе переразрешить зависимости и переписать lock. Сам стенд версию движка не проверяет: `ENGINE_VERSION = '9.0.0'` — константа в `lab/src/runner.js` и `lab/src/compare_models.js`, которая только печатается в отчётах (`engine.version`). Поставь в `node_modules` другую версию `simulation` — отчёты всё равно напишут «9.0.0», и preflight policy по движку (`lab/src/policy.js`) пройдёт.

## 2. Что сделать

### 2.1 Вендоринг — сделано нами, не трогать

`lab/vendor/simulation-9.0.0.tgz` и `lab/vendor/csv-parse-5.6.0.tgz` лежат в `main`: оригиналы из реестра, sha512 каждого равен `integrity` в `lab/package-lock.json`, происхождение и хеши — `lab/vendor/README.md`. `lab/vendor/` — защищённый путь: любое изменение там guard отклонит.

### 2.2 Установка из `lab/vendor/`, строго по lock, без сети

`lab/INSTALL.cmd` ставит зависимости через `npm ci` (строго по lock, а не `npm install`), только из `lab/vendor/`, без сети и без зависимости от содержимого пользовательского npm-кэша. Выбор способа — за исполнителем, с обоснованием в отчёте. Оба способа ниже мы проверили (Node 24, npm из его поставки, пустой временный кэш): установленные деревья `node_modules/simulation` и `node_modules/csv-parse` байт в байт совпадают с установкой из реестра.

**Способ A — lock и `package.json` не меняются.** Кладём tarball'ы в отдельный кэш и ставим из него офлайн:

```text
npm cache add ./vendor/simulation-9.0.0.tgz ./vendor/csv-parse-5.6.0.tgz --cache <каталог-кэша>
npm ci --offline --cache <каталог-кэша>
```

`npm ci` находит пакеты в кэше по `integrity` из lock. Каталог кэша — временный или внутри `lab/` в игнорируемом месте. `.gitignore` защищён: если нужен новый игнорируемый путь — используйте уже игнорируемый (`lab/node_modules/…`, `lab/output/…`) или системный временный каталог.

**Способ B — `file:`-зависимости.** В `package.json`: `"simulation": "file:vendor/simulation-9.0.0.tgz"`, так же для `csv-parse`. В lock у обоих пакетов меняется только `resolved` (на `file:vendor/…`); `integrity` остаётся прежним. Проверено: `npm install --offline` порождает ровно такой lock, после чего `npm ci --offline` с пустым кэшем проходит. Исполнитель без npm правит lock вручную — поле `resolved` и ничего больше.

`lab/package.json` и `lab/package-lock.json` — файлы разной конвенции: `package.json` в CRLF без перевода строки в конце, lock в LF с переводом строки в конце. Конвенцию сохранить (§9.2 п. 5).

### 2.3 Пин обеспечен стендом

- Стенд при каждом запуске, где участвует движок, читает версию **установленного** `simulation` (`node_modules/simulation/package.json`) и отказывается работать с понятной ошибкой, если это не `9.0.0`. Затронуты как минимум пути `RUN_LAB` / `RUN_TESTS`, `COMPARE_MODELS`, `CHECK_CANDIDATE`, `APPLY_PATCH` и самотесты. Лучше одна проверка в общем месте, чем копии по командам.
- В отчётах поле `engine.version` берётся из установленного пакета, а не из константы. Константа `9.0.0` остаётся одна — как ожидаемая версия пина.
- Новый случай в `QA_SELF_TEST` (`lab/src/qa.js`): подменённая версия движка приводит к отказу. Случай обязан реально падать, если проверку отключить: ветка провала бросает исключение или возвращает `false`, а не строку (урок Lab v0.9.1, контракт §8 п. 11). Подмену делать во временной копии, не в рабочем `node_modules`.
