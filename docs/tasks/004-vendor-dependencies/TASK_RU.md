# Задание 004 — вендоринг зависимостей стенда и обеспеченный пин движка (Lab v0.9.3)

Ветка: `task/004-vendor-dependencies` · Scope: `scope.json` рядом · Правила поставки: `docs/CONTRACTOR_DELIVERY_CONTRACT_RU.md` §9 · Порядок работы: `docs/tasks/README_RU.md`

## 1. Зачем

Стенд Orbital Economy Lab зависит от двух npm-пакетов: `simulation@9.0.0` (движок, AGPL) и `csv-parse@5.6.0` (MIT). Сейчас они скачиваются из реестра npm при установке, а `lab/node_modules` в git не хранится. Проект держится на точной воспроизводимости (`maxAbs = 0` между версиями модели), и движок заморожен (`lab/ENGINE_PIN.md`). Отсюда две проблемы:

1. **Воспроизводимость зависит от реестра.** Если пакет снимут с публикации или реестр будет недоступен, стенд не собрать. Нужно, чтобы сборка шла из байтов, которые лежат в репозитории.
2. **Пин объявлен, но не обеспечен.** `INSTALL.cmd` вызывает `npm install`, который вправе переразрешить зависимости и переписать lock. Сам стенд версию движка не проверяет: `ENGINE_VERSION = '9.0.0'` — это константа в `lab/src/runner.js` и `lab/src/compare_models.js`, которая только печатается в отчётах. Поставь в `node_modules` другую версию `simulation` — отчёты всё равно напишут «9.0.0», и preflight policy по движку пройдёт.

## 2. Что сделать

### 2.1 Вендоринг

- Положить в `lab/vendor/` оригинальные tarball'ы из реестра npm: `simulation-9.0.0.tgz` и `csv-parse-5.6.0.tgz`, **байт в байт те, что в реестре**, без перепаковки.
- Установка должна идти из `lab/vendor/`, без сети и без npm-кэша. Как это устроить (`file:`-зависимости в `package.json`, другой приём) — решает исполнитель; решение и причину описать в отчёте.
- `lab/package-lock.json` остаётся источником истины: `integrity` обоих пакетов **не меняются**.

### 2.2 Установка

- `lab/INSTALL.cmd` ставит зависимости через `npm ci` (строго по lock), а не через `npm install`.
- Установка не требует сети. Проверка: чистый checkout, пустой временный кэш, `npm ci --offline --cache <пустая временная папка>` проходит.

### 2.3 Пин обеспечен стендом

- Стенд при каждом запуске, где участвует движок, читает версию **установленного** `simulation` (`node_modules/simulation/package.json`) и отказывается работать с понятной ошибкой, если это не `9.0.0`. Затронуты как минимум `RUN_LAB` / `RUN_TESTS`, `COMPARE_MODELS`, `CHECK_CANDIDATE`, `APPLY_PATCH`, самотесты.
- В отчётах поле `engine.version` берётся из установленного пакета, а не из константы. Константа `9.0.0` остаётся одна — как ожидаемая версия пина.
- Новый случай в `QA_SELF_TEST` (`lab/src/qa.js`): подменённая версия движка приводит к отказу. Случай обязан реально падать при сломанной проверке — ветка провала бросает исключение или возвращает `false`, а не строку (урок Lab v0.9.1, контракт §8 п. 11).

### 2.4 Версия и документация

- Lab **v0.9.3**: баннеры `.cmd`, `src/cli.js`, `package.json` и `package-lock.json`, заголовки `lab/README_RU.md`, `lab/QUICK_START_RU.txt`, `lab/ENGINE_PIN.md`, `lab/docs/*.md`, где сейчас стоит v0.9.2 (исторические упоминания версий не трогать).
- `lab/CHANGELOG.md` — запись v0.9.3. `docs/HISTORY_RU.md` — строка v0.9.3 в таблице стенда.
- `lab/README_RU.md` §2, `lab/QUICK_START_RU.txt`, корневой `README.md` (раздел Quick start) — как теперь ставится стенд.
- `lab/ENGINE_PIN.md` — как пин теперь обеспечивается: байты в `vendor/`, `integrity` в lock, проверка версии при запуске.
- `lab/LICENSE-NOTICE.md` — сейчас там написано, что зависимости не поставляются вместе с проектом; это станет неправдой. Указать, что `lab/vendor/` содержит немодифицированные tarball'ы, под какими лицензиями (AGPL у `simulation`, MIT у `csv-parse`) и что текст лицензии лежит внутри каждого tarball'а (проверить, что это так).

### 2.5 Чего не делать

- Не менять версии пакетов, не запускать `npm update` / `npm audit fix`, не добавлять зависимостей.
- Не класть в git `lab/node_modules`.
- Не трогать защищённые пути (`model/`, `validation/`, `policy/`, `reference/`, `lab/input/`, `lab/reference/`, `BASELINE_MANIFEST.json`, `.gitattributes`, `.gitignore`, `tools/`). Если окажется, что без этого нельзя, остановиться и написать в отчёте почему.
- Не менять поведение проверок стенда сверх п. 2.3.
