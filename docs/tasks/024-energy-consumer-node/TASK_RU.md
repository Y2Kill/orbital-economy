# Задание 024 — тип узла `energy_consumer`: процессы подключаются к распределителю энергии колонии

Ветка: `task/024-energy-consumer-node` · Scope: `scope.json` рядом · Правила: контракт 1.9 §9, §9.2 п. 9 (контрольные точки и журнал), §9.4 · Порядок работы: `docs/tasks/README_RU.md`

## 1. Зачем

Planet v1 P3 (`docs/PLANET_V1_CONTRACT_RU.md`, решения владельца от 2026-10-02): энергию получают:

- добыча руды;
- добыча реголита;
- добыча энергоресурса — «энергия на добычу энергии», прежнее исключение снимается;
- производство оборудования.

Это 4 процесса × 2 колонии. Транспорт остаётся исключением с причиной. Новые потребители должны добавить порядка 10–20 % к нынешнему спросу на энергию.

Сейчас так подключены только металл, электроника и стройматериалы, и каждый — своей ручной ступенью модели. Одна механика повторяется 8 раз — это работа генератора узлов. Задача:

- тип узла `energy_consumer` (Lab v0.9.13);
- два расширения проверок, без которых узел не проходит аудит (§2.4).

**Модель, validation и policy не меняются.** Первым применением станет задача по модели v7.7.9: все четыре процесса одной декларацией.

### 1.2 Два вывода прототипа (они вошли в узел)

1. **Запрос читает сглаженный сигнал, а не плановый темп того же шага.** Без сигнала петли возникают у всех четырёх потребителей — проверено `loops` поочерёдно:
   - энергоресурс: запрос → желаемая генерация → спрос на топливо → добыча → запрос;
   - руда: доля выполнения → плавка → потребление руды → желаемая добыча;
   - оборудование и реголит: доля выполнения → плавка → прибыль завода → расширение → спрос на оборудование / стройматериалы → реголит.

   У стройматериалов (v7.7.4) петли нет, потому что их план не зависит от энергии того же шага; у новых процессов зависит.
2. **Собственные нужды энергетики обслуживаются первыми.** При пропорциональном урезании добыча топлива получает ту же долю, что и все. Тогда: меньше энергии → меньше топлива → меньше генерации. Это положительная петля с поглощающим нулём. Без приоритета колония B в Mode 46 к ~360-му дню падает в доли выполнения 0 навсегда: топливо 0, генерация 0, добыча 0. С приоритетом B держит 0.98. Так устроены и реальные энергосистемы: собственные нужды станций — первая очередь.

## 2. Узел `energy_consumer`

### 2.1 Декларация (строгая схема; незнакомое поле — ошибка с путём)

```json
{
  "type": "energy_consumer", "version": 1, "colonies": ["A", "B"], "switch": "Process Energy Enabled",
  "allocator": { "total": "{C} Total Requested Energy", "available": "{C} Available Generation",
                 "supply": "{C} Energy Supply", "ratio": "{C} Energy Fulfillment Ratio" },
  "consumers": [ {
    "consumer": "Power Resource Extraction",
    "rate": "{C} Power Resource Extraction Rate",
    "energy_per_unit": 0.05,
    "priority": true,
    "signal": { "initial": { "A": …, "B": … }, "adjustment_time": { "name": "…", "value": 3 } },
    "planet_process": "power_resource"
  }, … ]
}
```

Правила декларации:

- Один узел и **один переключатель** на несколько потребителей. Одна модельная ступень — один переключатель регрессии.
- Обязательны все поля, кроме `priority` (по умолчанию `false`).
- `signal.initial` — ключи ровно по `colonies`.
- `energy_per_unit` — конечное число > 0.
- Все четыре элемента `allocator` должны существовать в базе.
- `rate` — существующий элемент.
- Потребитель с тем же именем уже есть в базе (`X K Requested Energy` существует) — ошибка с именем.

### 2.2 Раскрытие (имена и формулы — как в прототипе; K — потребитель, X — колония)

**Общие элементы:**

- переключатель;
- `K Energy per Unit`;
- время подстройки сигнала (имя из декларации).

**На каждого K и X:**

- `X K Pre Energy Rate` — прежняя формула скорости дословно;
- STOCK `X K Energy Signal` и FLOW `… Increase` / `… Decrease` из `∅` / в `∅`. Форма — как у `X Power Resource Demand Signal`;
- `X K Requested Energy = IfThenElse(switch, signal × K Energy per Unit, 0)`;
- `X K Allocated Energy = request × ratio`. Для приоритетного K вместо общей доли — `X Priority Energy Fulfillment Ratio`;
- `X K Energy Fulfillment Ratio = IfThenElse(request > 0.001, allocated / request, 1)`;
- скорость := `IfThenElse(switch, pre × fulfillment, прежняя)`.

**Если в декларации есть приоритетные потребители** (на колонию):

- `X Priority Requested Energy` — сумма их запросов;
- `X Priority Energy Fulfillment Ratio = IfThenElse(prio > available, available / (prio + 0.001), 1)`;
- `X Priority Allocated Energy = prio × priority ratio`;
- общая доля := `IfThenElse(switch, IfThenElse(total > available, Max(0, available − priority allocated) / (total − prio + 0.001), 1), прежняя)`.

  Без приоритетных потребителей общая доля **не трогается**. Заметьте: при `prio = 0` новая формула совпадает со старой.

**Распределитель (на колонию):**

- `total := IfThenElse(switch, прежняя + Σ запросов, прежняя)`;
- `supply := IfThenElse(switch, прежняя + Σ выделенного, прежняя)`.

**Связи:** на каждую ссылку новых и заменённых формул, без дублей.

### 2.3 Фрагменты validation и слияние

- `energy_balance.consumers` дополняется потребителями. Новое поле **`priority`** — список приоритетных потребителей.
- `planet_closure`: у процесса `planet_process` ставится `energy: { kind: "requests", request: "{C} K Requested Energy", signal: "{C} K Energy Signal" }`; у приоритетного потребителя ещё `fulfillment: "{C} Priority Energy Fulfillment Ratio"`. Это касается и процесса, у которого стояло исключение (`kind: "none"` / `"exception"` с причиной). Слияние заменяет заглушку так же, как `deposit` в v0.9.12: содержательная декларация обязана совпадать, иначе конфликт.
- `open_boundaries`: потоки сигнала попадают в существующую `information_signal` (в прототипе так и вышло: 0 неклассифицированных).
- Повторное слияние идемпотентно. Если слияние ничего не меняет, файл копируется побайтно.

### 2.4 Два расширения проверок

1. **`planet_closure`, поле `energy.signal`.** Сейчас проверка близости «запрос и выход делят элемент планового темпа в пределах `max_hops`» не проходит через STOCK. Новое правило: если объявлен `signal`, обход **может пройти ровно этот сток**. При этом проверяется (каждое нарушение — ошибка процесса с именем):
   - `signal` — STOCK;
   - запрос читает его напрямую (1 ссылка);
   - все потоки стока идут из `∅` / в `∅`;
   - в `open_boundaries` эти потоки классифицированы как `information_signal`.

   Без `signal` поведение прежнее, побайтно.

   **Поле `energy.fulfillment` процесса** переопределяет общую `plugin.energy.fulfillment` для этого процесса: выход приоритетного потребителя читает приоритетную долю, а не общую. Без переопределения проверка `energy_output_to_fulfillment` находит общую долю только в 16 ссылках (через плавку и прибыль завода) и падает — так и вышло на прототипе.

   Схема плагина знает поля `signal` и `fulfillment`; незнакомое поле в `energy` — ошибка.
2. **`energy_balance`, поле `priority`.** Для каждого приоритетного K и колонии — runtime-соотношение `X K Energy Fulfillment Ratio >= X Energy Fulfillment Ratio` (с `abs_tol`). Строгая схема знает поле. Без поля — прежний набор проверок, побайтно.
